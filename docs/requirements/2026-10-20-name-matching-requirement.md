## 背景与问题

2026-10-16 处理成都智仁合光电有限公司整合序时账时，发现同一往来单位在账面存在多个写法（笔误字误、简称与全称混用、摘要解析残渣、工商更名、格式差异等）。当时以人工方式完成了 18 组归一合并、6 组工商核查判定和存疑清单，形成了一套完整打法，但流程是即兴执行的，无法复用。本任务把这套打法沉淀为开源技能，供日后序时账、台账及各类名单清洗复用。

## 用户与使用场景

- **用户**：审计/财务/尽调人员，以及执行此类任务的 AI 助手（用户无编程基础，技能须面向"说一句话就能跑"的交互）。
- **典型场景**：
  1. 整合序时账/明细账的客户、供应商、存货辅助列归一；
  2. 客商名单、供应商名录等 Excel/CSV 名称列的去重归并；
  3. 多来源（不同系统导出）汇表后的名称口径统一。

## 功能范围

**基本设计理念（用户 2026-10-20 明确，两轮修订后定稿）：尽量减少人工干预，且不把用户也答不了的题扔给用户。** 用户看到"博立叶/傅立叶"同样定不了，还得自己去查工商——所以候选对的判定顺序是：账内证据 → 机器自动查工商 → 定不了的才请人。人只处理机器连工商都查不清的残余，一次列清单一次拍板。

**候选范围客观化（用户 2026-10-20 质疑"真拿不准"范围过宽后修订）**：

- 自动合并仅限三种：清洗后一字不差；只差公司后缀词（有限公司/股份有限公司/（个体工商户）等）；简称完整包含于全称且开头地名一致。
- 其余名字相似的才进候选清单，每对必须打差异标签（疑似笔误 / 地名开头不同）；候选一次超过 50 对时先停下报数请示，防止清单淹没人工。
- **账内证据的限定用法**：仅两类构成证据——①同一发票号/票据号出现在两个名字的摘要里；②同日同额、一收一付对应。"同凭证共现"证明不了任何事（同一凭证可能是付款链条上的两家公司），**彻底删除该功能，连线索也不保留**。
- **工商查询（用户 2026-10-20 终稿口径）**：候选对账内证据定不了时，**机器自动查工商，不请示用户**（用户自己面对这类问题也得去查工商，没理由让用户徒手判断）。查的目的两个：①查登记真实全名，账上写错的按真名归一；②判定两个相似名是否同一家（都真实登记则分开，仅一家则合并）。"工商查询不是默认动作"指：不对每个名字无脑全查，只查定不了的候选对。仅当工商也定不了（查无此名、个体户无数据、结果矛盾）才请用户拍板。程序本身不联网，查询由执行任务的智能体按说明书调用 related-party-identification 的取数能力完成。

1. **通用名称归一引擎**（与业务场景解耦）：
   - 输入任意表格（Excel/CSV）的任意一个或多个名称列；
   - 规范化处理：空格、全半角、括号样式、编码前缀（如 `YF0001_`）、业务残渣前缀（如"入库（""冲销"）、截断补全等；
   - 候选对生成：规范化后完全一致的自动归并；近似名（字形近似、简称包含、后缀差异）生成候选对并附证据材料；
   - 产出标准化对照表（规范名称 / 原始称谓 / 涉及行数 / 归一依据 / 来源类型）与存疑清单。
2. **往来单位归一方法论层**（SKILL.md 正文）：
   - 证据分级：确定性格式差异（自动）→ 账内证据（同日凭证、发票号、同笔收付、专票佐证）→ 外部佐证（可选）；
   - 红线：法人不同不合并；拿不准一律不合并、进存疑清单；职员人名默认不参与归一（可配置）；
   - 口径约定：无法识别对象的占位处理（如"未列明供应商"）可配置；
   - 工商佐证**不是默认动作**：默认只用账内证据（凭证摘要、发票号、同日收付等）完成归一；仅当候选对账内证据不足以判定、且经确认确实需要时，才调用 `related-party-identification` 的取数层获取工商基本信息（法人、信用代码、股东）佐证，**不内置**联网取数代码。
3. **开源标准组合**：SKILL.md + README.md + LICENSE（AGPL-3.0）+ test-prompts.json。

## 明确不做的内容

- 不内置工商/联网查询代码（引用 `related-party-identification`，Q3=B）；**默认流程不触发任何工商查询**，仅在账内证据不足且确认需要时按需调用；
- 不做关联方关系认定（那是 `related-party-identification` 的职责）；
- 不改动账簿金额、科目、凭证等非名称内容；
- 不写死任何具体账套的来源优先级（明确否决"明细科目名录 > 辅助核算全称 > 摘要提取"式硬编码，Q1 通用化要求）；
- 不提供地址、产品名的专门清洗流程（引擎可复用，但方法论文档聚焦名称归一）。

## 约束与风险

- **错合风险**：近似名误合并会破坏账目口径 → 以分级合并（Q2=C）+ 红线 + 存疑清单控制，宁可漏合不可错合。
- **拟合风险**：方法论写成智仁合案例复盘 → 需求与测试均要求多场景输入（不依赖"客户/供应商/存货"列名约定，列由用户指定）。
- **环境约束**：Windows；Python 用本机 3.14；中文文件 UTF-8 with BOM；技能自包含，不依赖未声明的第三方服务。
- **发布约束**：AGPL-3.0，全文从 gnu.org 取原文；发布 Git 操作须用户逐次授权（CHECKPOINT 4）。
