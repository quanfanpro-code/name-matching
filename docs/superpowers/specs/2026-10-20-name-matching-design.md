# 设计文档：name-matching（名称归一技能）

- 日期：2026-10-20
- 阶段：方案设计（阶段 2）
- 状态：方案已经用户批准（检查点 2，用户选定做法三）

## 方案比较

| | 做法一：只写说明书 | 做法二：一个程序+说明书 | 做法三：分层（选定） |
|---|---|---|---|
| 做法 | 全靠人工智能照文档现场判断 | 洗名字与读写表格揉在一个程序里 | 洗名字工具与读写表格分开，说明书管业务判断 |
| 做事成本 | 最低 | 中 | 中偏高 |
| 结果可复现 | 做不到 | 做得到 | 做得到 |
| 换场景复用 | 不能 | 要拆程序 | 直接拿洗名字工具就走 |
| 维护成本 | 无程序可坏 | 一个文件全在里面 | 多一个文件，边界清楚 |
| 结论 | 不满足验收标准，弃 | 可行但不贴合已定的分层架构 | **选定** |

## 推荐方案（已批准）：三层结构

**第一层：洗名字工具（归一引擎，文件名 `归一引擎.py`）。** 只处理名字本身，不读不写任何文件。干三件事：

1. 洗干净：去掉多余空格、统一全角半角、统一括号样式、去掉"编码+下划线"前缀、去掉业务残渣前缀（如"入库（""冲销"）、补全被空格截断的名字。洗的规则是通用的，**不写死任何来源优先级**。
2. 找像的：把洗完还长得像的名字配成对（错别字、简称包含、后缀差别）。
3. 分三档（**按"尽量减少人工干预"设计**）：清洗后完全相同、只差公司后缀、简称包含于全称且开头地名一致的——**一律自动归一**；地名开头不同的近似名（防"天津/宿迁"式误并）以及疑似笔误的，才进"待定候选对"，**一次性列清单一次确认**，不逐对打断；既不像又不重复的单独成条。

**人工确认的提速设计**：候选对的判定顺序是"账内证据 → 机器自动查工商 → 定不了才请人"——**不把用户也答不了的题扔给用户**（用户看到"博立叶/傅立叶"同样定不了，也得去查工商）。账内证据仅两类：①同一发票号/票据号出现在两个名字的摘要里；②同日同额、一收一付对应。"同凭证共现"功能彻底删除（证明不了任何事）。候选清单每对带差异标签（【疑似笔误】如"博立叶/傅立叶"；【地名开头不同】如"天津满运/宿迁满运"），一次超过 50 对先停下报数请示。

**工商查询（机器自动执行，不请示用户）**：账内证据定不了的候选对，由执行任务的智能体按说明书自动调用 related-party-identification 取数能力查工商（程序本身不联网）。查的目的两个：查登记真实全名（账上写错的按真名归一）、判定两个相似名是否同一家（都真实登记则分开，仅一家则合并）。"不是默认动作"指不无脑全查，只查定不了的候选对；仅当工商也定不了（查无此名、个体户无数据、结果矛盾）才请用户拍板。

**第二层：读写表格（文件名 `整理表格.py`）。** 读 Excel 或表格类文件里用户指定的名字列，调第一层干活，把结果写成两个新文件：结果表（原表+规范名称列）和对照表（哪个名字并成了哪个、凭什么、涉及多少行），外加存疑清单。**永远不覆盖原文件**（遵守另存为的硬规则）。

**第三层：说明书（SKILL.md）。** 只讲业务判断：合并要有证据、法人不同不合并、拿不准进存疑、职员名字默认不参与、"未列明"占位怎么用、**工商查询不是默认动作**（账上证据够就不查，真不够了才去调用相关方技能的取数能力，见 0001 号决策记录）。

## 数据流

1. 用户给文件和列名（哪一列就是名字列，由用户说，程序不猜）；
2. 第二层读出全部名字，交第一层清洗、配对、分档；
3. 直接可并的先并；待定候选对连同证据材料列给用户（或执行任务的人工智能）确认；
4. 确认结果写回程序，第二层生成结果表与对照表，另存为新文件；
5. 全程记录：每个名字从哪来、并成了什么、依据是什么，可以倒查。

## 错误处理

- 文件找不到、列名对不上、名字列全是空 → 用中文明确报错，说清哪里不对、怎么改；
- 遇到空值、纯数字、超短名字（单字）→ 不参与配对，单独列出来提示；
- 任何出错场景都不动原文件。

## 测试策略

- 用 Python 自带的测试工具（不添新依赖），测试文件名用中文；
- 必须覆盖：正常路径（格式差异自动合并）、边界（空名字、单字名、纯数字名、上千个名字）、错误路径（文件不存在、列名错、空列）；
- 可复现测试：同一份输入加同一份确认决定，跑两遍结果必须一字不差。

## 迁移与回滚

- 新技能是独立目录，不碰任何现有技能；回滚就是删掉这个目录；
- 技能目录内单独初始化版本管理（按既有开源技能惯例），不影响上层目录；
- 发布前必须先过达尔文技能评估优化（用户硬性要求），评估不过不许提交推送。
